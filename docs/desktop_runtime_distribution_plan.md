# 桌面端自包含发行与组件更新重构方案

状态：源码、组件装配、三平台安装事务、更新/修复 UI、Release 验收链路及文档已接通。本地功能与故障恢复检查通过；新的正式安装器尚未在 GitHub Actions 完成构建、签名、原生安装和 GPU 实机验收，因此不能把源码完成称为发行验收通过。提交与推送按用户明确授权执行，发布仍须全部 Release 门槛通过。

本方案按 2026-10-12 确认的目标统一修订。下面的阶段是同一架构的实施顺序，不是互相独立的局部方案。只有全部必要能力和实际安装验收完成后才作为正式 Release 发布；提交、推送与发布仍需用户明确要求。

## 追加范围：桌面渲染与编辑功能收敛

按本轮用户追加要求执行，属于同一重构任务：

- 公式渲染固定使用内置 MathJax。删除设置中的引擎选择与 LaTeX 路径配置、渲染模式持久化、CDN/font 回退、LaTeX SVG 编译线程和缓存。主窗口、手写、识别结果、历史/收藏与 HTML 导出共享内置入口。
- 删除数学工作台入口、窗口、桥接、计算和主题/生命周期逻辑。桌面资源目录与 PyInstaller 清单不携带 MathLive 或 Compute Engine。
- 删除手写自动排版按钮、外部文档生成任务、完整 TeX 文档编辑窗口、编译消息处理、PDF 编译/预览、SyncTeX 定位及仅服务于此的源码查找/片段面板。
- 删除相应旧测试、翻译、用户文档入口和资源；不写删除存在性断言、不读取旧配置或加入迁移。

Office 插件仍需要 MathLive，其运行库/字体/许可已移入 Office `EditorAssets/vendor` 并由该项目独立持有。移动端功能维持其独立产品范围。PDF OCR、PDF 识别结果编辑保存及普通 Pandoc PDF 文件导出属于现有识别/导出能力，保留；后者仍要求外部 LaTeX 引擎，不再参与桌面公式预览。

追加范围的源码与资源清理已落实。Qt 本地 MathJax 转换/预览、模型完整性与共享缓存选择、资源窗口反复打开、Office 独立资源链路均有对应验证。模型资源窗口不添加最小尺寸约束。应用诊断订阅实时预热状态，重新打开也读取当前状态；更新窗口使用 Fluent 不定进度条和 Markdown 发布说明。具体检查结果以提交前的本地检查及后续 Release 验收记录为准。

## 1. 最终产品行为

桌面端拥有并维护自身完整运行资源。安装包部署应用主体、独立推理 Python、锁定依赖、识别模型和 Pandoc。Windows/Linux 提供 CPU 与统一 GPU 发行，macOS 固定 CPU。正常安装后首次启动直接进入主窗口并后台预热，不要求用户安装 Python、配置 CUDA/cuDNN 或先进入依赖向导。

GPU 发行携带实际需要的 CUDA 用户态运行库与 cuDNN，复用系统 NVIDIA 驱动；不安装完整 CUDA Toolkit、编译器或显卡驱动。兼容范围依据显卡架构、驱动最低要求及实际推理验收确定，不依据用户系统的 CUDA Toolkit 或 cuDNN 安装版本选择下载包。

应用内删除“依赖管理”及其环境目录、解释器、后端切换、包安装和独立卸载入口。CPU/GPU 是安装时确定的发行属性，保存在安装元数据中，不再是用户配置中的可变偏好。更换发行类型通过对应安装器执行；日常更新保持已安装的发行类型。

设置保留面向用户的模型、识别和其他业务选项，并提供应用版本、运行状态、诊断、日志及安装资源修复能力。修复属于发行资源维护，不重新暴露 Python/pip 或依赖分层界面。

更新采用组件级增量：只下载发生变化的组件，每个下载组件均为可独立校验的完整载荷。首次安装载体与日常更新载荷分开，二者使用同一份发行清单、组件身份和安装适配器。

### 固定约束

- 三平台默认资源位于实际安装位置，由平台安装与更新机制维护；不允许用户在应用内另选解释器或依赖目录。
- UI 与推理保持进程隔离；UI 只使用自身冻结依赖，推理通过明确的 worker 协议调用随包 Python。
- 构建时锁定 Python、ORT、全部传递依赖和运行库的确切构建与摘要，不在用户机器上运行 pip 解析版本。
- 每个推理组件只含一个 ORT 发行包；组件更新整体替换，不在旧 site-packages 上叠加安装。
- 不依赖系统 Python、用户 site-packages、系统 CUDA/cuDNN 或旧配置中的路径启动发行程序。
- 用户数据与安装资源分开，模型损坏修复缓存仍属于用户数据；不另建可自由切换的推理环境。
- 不保留旧依赖层、旧环境发现、旧启动标志、旧安装包解析或配置迁移兼容逻辑。
- 源码运行采用开发者选择的 Python 和标准开发工具，开发依赖不由应用代管，也不要求固定仓库路径。
- 正式发行由 GitHub Actions 构建；不新增本地环境收集和本地打包链路。
- 不写墓碑测试；删除仅服务于被移除行为的测试、翻译和文档。
- 本方案处理桌面端，Office 插件和移动端仍按各自明确的资源协议管理。

## 2. 资源边界与状态归属

| 对象 | 内容与职责 | 唯一所有者 |
| --- | --- | --- |
| 应用组件 | PyInstaller UI、业务和预览资源、随包 Pandoc、应用侧 worker 启动与协议代码 | 安装及更新服务 |
| 推理组件 | 独立 Python、推理依赖、唯一 ORT；GPU 发行额外包含匹配运行库 | 安装及更新服务 |
| 模型组件 | 全部识别模型和配套文件、模型清单 | 安装及更新服务；模型服务负责只读使用与损坏修复 |
| 安装身份 | 平台、架构、CPU/GPU 发行类型、实际组件身份与内容摘要 | 本地安装清单 |
| 运行状态 | worker 存活、预热、实际执行提供者、识别任务和异常 | 各运行控制器 |
| 用户数据 | 业务偏好、历史、收藏、日志、下载缓存和模型修复缓存 | 统一用户数据路径及对应业务服务 |

安装清单描述实际部署内容，不冒充健康检查结果。后端由安装身份和实际推理组件确定，不另外保存用户后端偏好、环境根目录、解释器路径或层状态文件。

应用侧 worker 协议与推理组件声明兼容范围。UI、推理和模型在运行上解耦，但不能任意组合版本；一次发布清单必须指定经过验证的完整组合。业务更新无需更换未变的推理组件，涉及协议或依赖要求变化时，更新计划同时升级必需组件。

源码模式使用同一套控制器和 worker 协议，发行路径解析与开发路径解析集中在启动装配边界。开发者用标准项目环境提供依赖，不在设置中保留开发专用环境管理入口或用生产配置启动另一套 Python。

## 3. 自包含构建与部署

### 3.1 发行配置

在 `packaging/runtime/` 集中维护构建配置、依赖锁定和资源来源。平台脚本读取同一份数据，不分别维护 CUDA 到 ORT 的判断。每个配置至少包含：

- 平台、架构、CPU/GPU 类型和稳定组件标识。
- 独立 Python 来源、补丁版本、ABI、归档摘要和再分发资料。
- 公共推理依赖的完整锁定结果、ORT wheel 构建和摘要。
- GPU 运行库清单、确切版本、摘要、最低驱动和显卡支持范围。
- 模型清单、Pandoc 构建、worker 协议与模型格式要求。
- 组件归档内容、平台安装载荷、签名及许可文件。

统一 GPU 发行以 CUDA 12.8、cuDNN 9.8 和明确的 CUDA 12.8 ORT 构建作为初始评估组合，装配一套固定的私有运行库。确切 ORT wheel、运行库补丁版本、摘要与裁剪清单在阶段 1 验证后锁定，不能把候选组合写成已经验收的发布能力。支持范围优先考虑显卡覆盖，不因版本号更新而直接改用 CUDA 13，也不依据用户系统安装的 CUDA 版本复制发行包。

#### GPU 覆盖目标与驱动验证基线

| 架构 | 常见显卡 | 验收定位 |
| --- | --- | --- |
| Turing | GTX 16、RTX 20、T4 | 主要支持目标 |
| Ampere | RTX 30、A100、相应 RTX A 系列 | 主要支持目标 |
| Ada | RTX 40、RTX Ada 系列 | 主要支持目标 |
| Blackwell | RTX 50、RTX PRO Blackwell | 支持目标，核对具体 ORT 构建的架构代码和实际 OCR |
| Maxwell/Pascal/Volta | 部分 GTX 900、GTX 10、Titan V、V100 | 条件性覆盖，分别核对 Windows/Linux wheel 后再验收，不预先承诺 |

CUDA 12.8 对应的 cuDNN 9.8 支持矩阵包含上述架构，但最终覆盖范围是 ORT 构建、CUDA/cuDNN 库、显卡、驱动和本应用模型共同支持的交集。Windows 与 Linux wheel 的架构目标可能不同；不能只根据 cuDNN 表格或显卡系列名判定本产品可用。

驱动验证基线采用 Windows >=570.65、Linux >=570.26，来自 CUDA 12.8 GA 对应的驱动版本。驱动同时必须支持具体显卡型号；较新型号可能要求更高版本。这是保守发布验证基线，不宣称它是所有 CUDA 12.x 应用的绝对最低驱动，也不未经实测依赖次版本兼容降低要求。

AMD、Intel 显卡及 macOS 使用 CPU 发行。未覆盖的 NVIDIA 硬件或驱动给出明确诊断与 CPU 发行说明，不自动下载安装另一套环境。用户无需安装 CUDA Toolkit/cuDNN。最终验收记录注明确切显卡、驱动、ORT/运行库版本和实际执行提供者，不把本机一次成功推广为整个系列已验证。

依据：[cuDNN 9.8 支持矩阵](https://docs.nvidia.com/deeplearning/cudnn/backend/v9.8.0/reference/support-matrix.html)、[CUDA 12.8 驱动版本表](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html)、[ORT 构建架构说明](https://github.com/microsoft/onnxruntime/pull/23671)。实际发布仍以锁定 wheel 的构建内容为准。

| 平台 | 发行类型 | 发布要求 |
| --- | --- | --- |
| Windows | CPU、统一 GPU | CPU 离线识别；GPU 在目标显卡与驱动范围完成真实 OCR |
| Linux | CPU、统一 GPU | 同上，并满足系统库下限、动态库定位和平台安装要求 |
| macOS | CPU | 对正式支持的架构验证完整独立环境、签名和离线识别 |

发行类型共用产品身份与应用实现。首次安装器可部署完整资源，应用更新载荷按平台和架构共享，推理更新载荷再区分 CPU/GPU。资源身份由清单提供，不从文件名推断 CPU/GPU 或 CUDA 版本。

### 3.2 逻辑资源位置

```text
<安装资源根>/
  application/                 应用主体与业务资源
    pandoc/                    随应用组件部署的 Pandoc
  inference/                   完整独立 Python、依赖及 ORT
    native/                    GPU 发行的匹配用户态运行库
  models/                      模型和配套资源
  distribution.json            实际安装身份及组件清单
```

平台物理布局由 `runtime.installation_layout` 集中定义：Windows 使用安装根的三个组件及 `distribution.json`；Linux 使用 `/usr/lib/latexsnipper` 的 dpkg 归属组件，安装身份放在 `/var/lib/latexsnipper/distribution.json`；macOS 使用 `.app/Contents/Resources/desktop`，外层签名应用整体重建。默认资源不写入构建机绝对路径或用户配置中的环境目录。

安装组件按不可变载荷管理。程序正常运行不执行 pip、不修补 site-packages、不修改系统 PATH，也不下载缺失 CUDA DLL 到任意共享目录。worker 启动时只为该子进程配置私有库搜索路径，避免系统 CUDA/cuDNN 或外部 Python 配置污染，不改变整个 UI 进程的依赖来源。

### 3.3 Python 与 GPU 运行库裁剪

三平台统一执行“获取独立 Python → 安装锁定依赖 → 装配必要运行库 → 按实际调用裁剪 → 搬移与隔离验证 → 平台签名”。

- 验证解释器、标准库、扩展模块、SSL 和 ORT 不引用构建机或系统 Python。
- Windows 的相对 `._pth`、Linux ELF 搜索路径与系统库下限、macOS Mach-O 路径和签名属于平台适配。
- 不沿用旧模板只保留 pip/setuptools/wheel 的白名单；推理依赖完整性以真实调用和资源清单验证。
- 不为用户建私有环境而保留 venv/ensurepip/pip。发行运行不使用的安装工具可裁剪；被真实运行依赖引用的资源、元数据和许可证必须保留。
- GPU 只携带 ORT 实际需要及其传递依赖的可再分发运行库，不带编译器、开发头文件和驱动。
- 记录压缩前后体积，验证裁剪后的模型加载和真实推理，不以任意体积目标替代功能验收。

### 3.4 模型与 Pandoc

全部模型在构建时按既有模型清单获取、校验并部署。保留模型缺失或损坏的自动修复，复用既有模型服务和下载能力。修复缓存按目标模型内容身份校验，只覆盖对应损坏资源，不能以旧缓存遮蔽升级后的模型；完好模型不重复复制或下载。

Pandoc 只从应用组件内定位，随该组件安装、更新和卸载。删除独立 Pandoc 下载、镜像测速、共享工具目录、PATH 增删和持久化可执行路径。发行程序缺失 Pandoc 时报告安装异常并修复应用组件，不用任意系统版本掩盖损坏。

源码运行可使用开发者提供的 Pandoc，不把开发路径持久化为发行资源位置。PDF 导出所需 LaTeX 引擎仍是明确的外部工具，与推理环境无关。

## 4. 安装、启动、诊断、修复与卸载

### 4.1 安装与启动

首次安装直接部署发行清单规定的完整组合。正常首次启动进入主窗口，快速入门按已有业务偏好显示，后台预热当前模型。GPU 发行检查显卡、驱动与私有运行库加载结果，不探测系统 Toolkit 版本来选 ORT。

资源损坏不会阻止 UI 启动：相关能力标记不可用，给出具体诊断和资源修复入口。GPU 不可用时说明驱动、硬件或载荷问题，不静默改写发行类型，不偷偷安装 CPU 环境。识别正常使用期间不重复整套校验或阻塞等待 pip。

### 4.2 修复

修复和更新使用同一资源清单、下载器、校验与安装事务。修复恢复当前发行版本的明确组件，不把“修复”实现为逐包安装、升级依赖或重建用户自定义环境。

模型修复可通过已有可写缓存恢复对应内容；应用、Python、ORT 或 GPU 库损坏时恢复所属发行组件。受保护安装目录由平台安装器取得必要权限；macOS 不在运行中的签名 `.app` 内直接写入修复文件。

诊断界面只显示实际组件、模型、执行提供者和错误，提供日志、检查更新及修复入口，不保留依赖层勾选、环境终端、解释器切换或独立环境卸载。

### 4.3 卸载

平台卸载机制移除所有归属本产品的应用、推理和模型安装组件。用户数据按既有明确选项保留或删除，模型修复缓存与更新缓存属于用户数据。

删除“共享工具”“私有 Python 环境”和“单独卸载依赖”的卸载选项及临时清理脚本。卸载不扫描旧目录、不迁移历史数据、不触碰用户系统 Python、CUDA Toolkit、cuDNN 或显卡驱动。

## 5. 完整组件更新协议

### 5.1 清单与更新计划

每个 Release 发布签名或具有等效可验证来源的结构化清单。清单统一描述产品版本、平台、架构、发行类型、目标组件身份、协议兼容范围、下载地址、长度、摘要和平台签名资料。安装器和更新器共用该协议与验证代码。

本地安装清单记录当前真实组件内容身份。更新计划由目标清单与本地状态生成，不能仅根据产品版本、资源扩展名、资源排序或更新缓存文件名选择安装包。找不到匹配资源或出现重复身份时明确失败，不猜选另一个发行类型。

| 变化 | 下载与应用行为 |
| --- | --- |
| 仅业务与预览修改 | 更新应用组件，保留符合目标清单的推理与模型组件 |
| Python/推理依赖/ORT/GPU 运行库修改 | 下载当前发行类型对应的完整推理组件，整体替换 |
| 模型或配套文件修改 | 更新模型组件，失效的修复缓存不参与新版模型加载 |
| 协议或兼容范围修改 | 同一事务更新目标清单要求的全部组件 |
| 本地组件损坏 | 恢复目标版本的所属完整组件，校验缓存后才可复用 |

跨任意仍受目标协议支持的版本直接生成目标组合，不依赖相邻版本补丁或历史文件。未变组件必须确认内容符合目标清单；不能只看版本号就认为本地完整。组件级增量的含义是“未变组件不下载，变更组件完整更新”，不宣称它是文件级或二进制差分。

### 5.2 下载、安装与失败恢复

统一任务状态为检查、下载、校验、等待安装、应用、验证、完成或失败；状态由更新任务控制器维护，窗口只订阅状态与进度。

1. 验证目标清单、适配条件与存储空间，计算完整更新计划。
2. 下载到临时缓存，校验长度、摘要与要求的签名。缓存身份包含平台、架构、组件内容身份，CPU/GPU 同版本资源不得混用。
3. 准备完整目标资源，不在下载过程中覆盖当前组件。取消和断网保留当前版本可用。
4. 通过既有生命周期服务停止任务与 worker，等待应用退出；由独立安装进程完成替换，不在活动 Qt 回调中删除窗口或应用对象。
5. 由平台适配器安装整个目标组合并记录事务。只有部署和验证成功后才提交新安装清单。
6. 新版执行轻量协议与资源检查；失败时由事务恢复更新前的安装状态，报告真实结果，不能留下新 UI、旧不兼容 worker 与错误清单混合运行。修复损坏安装时，恢复原状态不代表原安装已恢复健康。

仅保留当前部署事务所需的临时备份，验证成功并提交后删除。这里的恢复指安装中断或验证失败时恢复更新前的安装状态，不提供历史版本列表、手动降级入口或长期保留的旧版本。恢复不涉及旧依赖层、旧目录或旧配置的迁移兼容。未完成事务在再次启动时先恢复或完成，不能把半安装资源当作正常环境。

下载复用暂停、取消、断点续传与校验能力。只有可暂停下载显示暂停动作，安装与验证不能伪造暂停。Fluent `ProgressBar` 显示下载百分比；`IndeterminateProgressBar` 在检查、校验及交接阶段显示动画。发布说明在窗口内按 Markdown 呈现，即使当前 Release 没有组件目录或源码运行，也能独立显示说明。窗口关闭确认、销毁后断开信号、取消后忽略迟到回调和实时日志订阅统一保留。

### 5.3 平台安装约束

- Windows：更新进程在 UI 与 worker 退出后替换资源，处理文件占用和安装目录权限；全部可执行载荷按发行要求签名。
- Linux：组件载荷与包管理器的文件归属、依赖及卸载一致。受包管理器管理的文件通过相应组件包和安装事务更新，不直接解压覆盖 `/usr` 造成数据库与文件失配。离线首次发行包含完成安装需要的组件载荷。
- macOS：在暂存位置按目标清单重建完整 `.app`，复用未变载荷，验证整个应用签名后再替换。发布清单单独携带目标组合对应的签名封印载荷及精确文件清单，不能在原 `.app` 中局部替换文件后假称签名仍有效。

安装布局、平台签名与更新组件必须共同设计并验收。若某个平台的拟定布局无法独立装配和验证组件，修改布局或载荷边界后再实现；不能以长期整包重装旁路掩盖不成立的组件协议。

| 目标模块边界 | 职责 | 不承担的职责 |

对现有源码逐项删除下列职责及其全部调用方：

- `runtime/dependency_runtime.py`、`dependency_python.py`、`environment_terminal.py` 中的环境发现、依赖根覆盖、路径注入和环境终端入口。
- 系统 CUDA/cuDNN 到 ORT 下载版本的运行时映射、未知版本猜选和自动安装修补；保留适用于私有运行库与驱动诊断的真实能力。
- 用户配置中的依赖目录、外部解释器、后端偏好和依赖层字段；不读取、转换或迁移旧值。
- 环境变量中的强制私有 Python、强制进向导、已进入标志、依赖根覆盖、手动 CUDA 版本等旧控制通道。逐项确认读取方；保留真正必要的平台变量或子进程参数，集中在启动边界传递，不再增加第二套配置来源。
- Pandoc 独立安装、共享工具发现、PATH 修改、可执行路径持久化、卸载复选框和共享工具清理脚本。
- 基于旧安装包文件名挑选资源、仅按产品版本复用下载缓存及整包安装中心的更新流程。
- 仅服务于这些入口的设置控件、回调、翻译、测试、文档与空壳转发模块。

有真实用途的下载控制、进度和生命周期能力移动到其最终所属模块，再删除旧调用链。库自身的独立 Python 使用接口按其公开用途保留，不因为桌面移除环境选择就错误删除其他真实使用方。

## 7. 已落实的实现与发行验收门槛

### 7.1 协议与构建输入

- `distribution_manifest` 严格声明平台、架构、CPU/GPU 类型、三个组件、内容身份、协议和模型格式。发布身份含首次安装载体及 macOS 封印；安装身份只保留实际组件组合和发布标签，避免载体/签名资源的自引用摘要。
- `component_inventory` 和 `component_archive` 核对文件摘要、长度、类型、符号链接边界与额外内容。更新和安装共用同一份目标身份，不猜测旧文件名。
- `sources.lock.json` 固定独立 Python 3.11.17、ORT 1.26.0、CUDA 12.8、cuDNN 9.8.0.87 的来源和摘要；`dependencies.lock.json` 固定三平台全部推理归档。
- `resources.lock.json` 固定 MathCraft Models v1.0.0、Pandoc 3.12.1 及许可来源。正式模型由官方资源生成，不收集用户缓存。
- 源码运行使用开发者选择的 Python；客户端不执行 pip、不发现旧环境或迁移配置。

### 7.2 装配与已有本地实测

共享构建脚本按锁定来源装配应用、推理、模型与 Pandoc。应用和推理使用分开的输入指纹缓存；仅模型变化不强制重新冻结应用或装配推理。Windows/Linux 两种发行共用同一应用载荷。

Windows 独立推理原型完成目录搬移、CPU 算子与 OCR 验证。GPU 在 RTX 4050 Laptop（Ada，CC 8.9）、驱动 610.88 上完成真实推理及私有库审计。该记录仅证明此设备与原型，不能推广为全部 GPU 或正式安装器已验收。

| Windows 推理原型 | 未压缩内容 | 首轮 ZIP 载荷 | 私有 GPU 库 |
| --- | ---: | ---: | ---: |
| CPU | 约 371 MiB | 约 136 MiB | 无 |
| GPU | 约 2.93 GiB | 约 1.84 GiB | 约 2.25 GiB |

正式模型资源为 14 个文件、219,454,786 字节。Windows 锁定 Pandoc 已通过确切版本和 DOCX、ODT、PPTX、EPUB、HTML、Typst、纯文本实际导出。上述体积不含 GUI 与首次安装载体，不能当作最终发行大小。

### 7.3 独立部署与恢复

- `component_controller` 在后台执行检查、下载、校验与交接；Qt 窗口订阅状态。暂停仅作用于下载。销毁后忽略迟到结果，取消保持当前资源。
- `updater_entry` 不加载 Qt，部署前独立重新认证指定发布清单，等待 UI 和 worker 退出。原权限 watcher 在结束后重新启动应用；不会以管理员身份启动日常 UI。
- Windows 按同卷目录替换组件，验证后提交清单和根启动器；暂时保存原内容用于失败恢复。
- Linux 把已验证载荷生成独立组件 deb，通过 dpkg 移除、安装或恢复文件和包归属。可变安装身份不属于包内静态文件。
- macOS 在应用旁侧重建目标 `.app`，复用未变组件，使用精确清单验证外层封印，再检查 codesign、stapled ticket、Gatekeeper 和 worker。用 Darwin `RENAME_SWAP` 原子交换整个应用，通过目录身份保证重复恢复不会再次交换。
- 事务记录持久化并串行部署；未完成事务在启动前恢复。成功后删除当前事务备份，不提供历史版本列表或手动降级。
- 首次离线安装及 Windows/Linux CPU/GPU 重装使用共享完整部署入口；常规更新保持当前发行类型。

行为测试覆盖断点下载、完整性、源认证、取消、窗口销毁、组合级提交、首次安装中断、部分安装失败、Linux 包归属恢复及 macOS 重复恢复。平台系统调用的模拟测试不等于实际签名或原生安装验收。

主窗口、编辑结果和手写预览共享公式/文档片段解析，避免把带标题、正文、分段公式和 SVG 图的内容整体包入数学模式。Qt 实测覆盖同一复杂输入的两种页面：14 个公式与 1 张静态 SVG 图均正常，MathJax 错误为 0；另外通过 3 组 SVG/MathML 转换和 8 类 CHTML 页面。

### 7.4 Release 构建与卸载

`release.yml` 构建 Windows x86_64 CPU/GPU、Linux x86_64 CPU/GPU、macOS arm64 CPU 五个目标：

1. 构建一次公共模型资源，按平台装配应用及推理组件。
2. Windows 必须签署新 PE 载荷与安装器；macOS 必须签署应用并公证、附票据，再签署 DMG。无 unsigned 发布后备。
3. Windows 生成 Inno 安装器；Linux 离线归档含完整载荷和基础 deb，APT 仅解析系统 GUI 依赖，组件通过 dpkg 安装；macOS 生成 DMG。
4. 签名完成后生成组件摘要及载体身份，校验最终目录，发布结构化清单与 SHA256SUMS。
5. 新 runner 执行实际首次安装、发行类型重装、损坏模型修复与卸载；独立 CUDA runner 执行真实公式、文字及混合 OCR，核对私有库加载位置。
6. 所有构建、签名、原生安装及硬件门槛通过后才允许发布。手动构建默认不发布。

Windows 卸载拥有三个安装组件；Linux 由基础包和三个组件包归属；macOS 删除应用。用户数据与共享模型缓存分别提供明确清理选项。清理不搜索旧环境，不影响系统 Python、CUDA、驱动或用户导出目录。

### 7.5 当前验收边界

本地使用开发者指定 Python 执行全套功能测试、类型检查、编译、翻译检查和 workflow 静态检查。常规 CI 保持轻量，只保留源码编译、锁定输入、翻译、注释和已有 Office 构建检查；不增加全套 pytest/pyright 或三平台开发依赖安装。

正式安装器仅在 GitHub Actions 构建。目前没有本轮新安装器的 CI 构建、SignPath/macOS 签名、Linux/macOS 原生安装及跨硬件 CUDA 验收记录。发布前需要配置签名凭据、Windows 递归组件签名规则、两个 CUDA runner，并通过对应门槛。实际 macOS 应用身份/系统权限和全部支持显卡范围也以原生产物实测为准。

## 9. 主窗口控制器组合现状与目标衔接

主窗口已改为控制器组合，负责创建界面、注入依赖、连接信号及转交 Qt 事件。布局模块只构造控件，不拥有模型、识别线程、历史或运行状态。

| 所有者 | 状态与资源 | 目标协作 |
| --- | --- | --- |
| `ModelRuntimeController` | 当前/期望模型、后台预热、MathCraft 进程引用 | 模型选择和预热；发行资源解析注入，删除现有环境选择接口 |
| `RecognitionTaskController` | 当前 worker/thread、准备请求、取消与关闭状态 | 图片/PDF 共用准备、启动、结果分发和线程回收 |
| 图片/PDF 控制器 | 输入校验、请求构造、选项、进度与结果窗口 | 使用任务控制器，不复制线程或忙碌状态 |
| `RecognitionResultController` | 确认窗口、屏幕位置、通知限频 | 调用历史与导出，不推断其他控制器私有状态 |
| `PreviewController` | 内容、渲染记录、MathJax 预览和防抖计时器 | 提供明确的内容与刷新接口 |
| `HistoryController` | 历史、标签、类型和持久化 | 明确查询与修改接口供收藏及结果调用 |
| `WindowController` | 设置、收藏、手写窗口 | 窗口 owner 只用于 Qt 归属和位置，不作为服务查询入口 |
| 截图、快捷键、托盘和主题控制器 | 各自注册资源、覆盖层、菜单与计时器 | 只管理所属资源 |
| `StatusController` | 状态栏与通知 | 订阅模型和任务实际状态 |
| `AppLifecycleController` | 关闭状态与资源清理顺序 | 停止任务和 worker；向更新安装进程交接，不跨模块重置字段 |

设置窗口通过明确 context 获取业务服务；修复和更新提供独立的明确服务接口，不重新将路径选择塞入模型控制器。取消准备请求使请求标识失效，迟到回调不能重新启动取消任务。结果在 GUI 线程分发后才回收线程；关闭时各所有者结束任务，最后关闭日志。

这些 UI 边界继续使用；环境选择与依赖管理协作已按第 6 节删除。发行 readiness 由第 7 节的实际验收门槛确定。
